## Proposed request and operator workflow

This is a reviewable procedure to complete after the missing channel/policies and authorized operator implementation exist. It does not expose an inactive form or authorize a live deletion/export today.

1. Receive the request through the owner's approved private channel. Record a request reference, received time, requested action and minimal contact/verification context. For a teaching report, retain the topic, page and official question ID. Do not require passwords, verification codes, cookies or payment details.
2. Acknowledge receipt using approved Hebrew copy and the actual supported scope. Make no completion-time promise until the owner supplies a policy and staffing commitment. Potentially unsafe teaching goes immediately through the existing Operations content-safety process; it does not wait for a data-request batch.
3. Verify control of the relevant account through an approved authenticated/recovery mechanism, and resolve ambiguous identity without disclosing another learner's existence. The current gateway has no export/delete endpoint; a future implementation must retain origin/CSRF, session and learner-scoped checks. Use trusted mapping, never a user-supplied learner UUID as authority.
4. The operator lists only the verified learner's affected record classes from this inventory. Resolve open reset barriers, access state, entitlement timing, completed topics, active sessions and any approved evidence-retention exception. Have the owner/policy reviewer decide what is removed, anonymized, retained and disclosed before execution. Do not substitute subscription lapse cleanup for account deletion.
5. For an approved export, build a bounded learner-scoped personal-data artifact through trusted server/database reads. Review ownership and fields, omit secrets/private keys/other learners, and use an owner-approved private transfer destination. Choose artifact expiry through policy, not this draft. Log only the request reference, scope and outcome, without exported content.
6. For an approved deletion, use a reviewed, tested operator path with a dependency-aware transaction/provider sequence. Block affected app access as required, revoke gateway/provider sessions and handle referenced learner/profile/progress/attempt/completion/grant records according to the approved scope. FK restrictions and the entitlement timing trigger must be addressed by a deliberate reviewed implementation. Do not disable integrity checks or blindly delete Auth first.
7. Verify denial through the gateway and direct provider/database boundaries where applicable. Verify no other learner changed. Reconcile provider failures before reporting completion. Record outstanding backup/provider retention separately, with the approved treatment of a future restored copy. A partial provider result must produce a truthful partial outcome, not a completed deletion claim.
8. Notify the requester only through the approved verified channel, identifying completed scope and any approved retained scope. Close the private request record according to policy. Track code/source fixes and exact approvals in existing Operations records; do not copy private learner details into public issues.

No new retention durations, consent mechanism, deletion deadline, export download URL or commercial/legal promise is selected here. The owner and qualified reviewer must resolve these policy questions before public account opening. The final implementation should be tested with disposable owned synthetic identities, never production learner data.
