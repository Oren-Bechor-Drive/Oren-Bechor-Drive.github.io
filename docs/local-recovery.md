# Local recovery rehearsal

Run this from the repository checkout after `npm ci`:

```bash
npm run rehearse:recovery
node --test tests/database/recovery.test.mjs tests/database/gateway-sessions.test.mjs
```

The rehearsal starts two independent PostgreSQL fixtures on IPv4 loopback, applies the checked-in migrations and seeds only synthetic learner data. It exports the source fixture into an in-memory archive, restores it into the untouched target fixture and prints a JSON report containing `scope: "local"`, named checks, migration filenames and elapsed milliseconds. The report contains no archive bytes, encryption key, credentials or session ciphertext. A failed check exits unsuccessfully. All connections, database directories and temporary synthetic media are removed in `finally`, including after failed assertions. No dump file is written.

The command has no URL, destination path, credentials or other arguments. It does not read application environment files, connect to hosted Supabase or export real learners. The same restrictions apply to the exported `rehearseLocalRecovery()` function. [Database verification](../supabase/tests/README.md#local-tests) explains the minimal Auth fixture and its limits.

## Archive and restore contract

Only an instance created by `startDatabase()` in [database.mjs](../tests/support/database.mjs) has `dumpData()` and `restoreData(bytes)`. [database-recovery.mjs](../tests/support/database-recovery.mjs) checks that fixture's ownership and loopback connection. A closed fixture cannot export or restore. The helper accepts no remote URL, connection settings or filesystem destination.

The versioned archive includes hashes and filenames for the migrations actually applied, the Auth-bootstrap hash, the relation and column manifest, foreign-key metadata and a schema hash. PostgreSQL exports ordinary tables in `auth`, `public` and `private` within one read-only repeatable-read transaction. Each row remains the exact `row_to_json(row)::text` string generated by PostgreSQL. JavaScript does not parse row numbers, so bigint revisions and counters above its safe integer range survive unchanged.

The target independently discovers its catalog and must match the archive and the schema captured when that fixture started. Unknown relations, columns, changed migration hashes or schema drift are refused. A target must still contain only its initial migration data. This permits the migration-owned session-control singleton while rejecting inserted learners, sessions, content or changed singleton values.

Restoration locks the allowed tables and replaces their rows in one local-admin transaction. It binds each original JSON string to `jsonb_populate_record`, using identifiers from the verified target manifest. Fixture-only `SET LOCAL session_replication_role = replica` avoids circular foreign-key and immutable-row trigger ordering during insertion. Before commit, the helper checks every fixture foreign key with its parent/child columns, equality operators and `MATCH SIMPLE` or `MATCH FULL` null rules. Any orphan row aborts restoration. Rollback preserves the target's initial rows, and commit or rollback restores normal trigger behavior.

The pinned embedded package contains `postgres`, `pg_ctl` and `initdb`; this rehearsal uses the existing `pg` client and does not require `pg_dump`, `pg_restore` or system-package installation. It rehearses application rows against source-controlled migrations. It is not a complete Supabase backup or a test of a provider's dump format. Roles, full Supabase Auth internals, extensions, Cron configuration, deployment secrets and external providers remain outside the archive.

## Checks and separate recovery material

[The rehearsal](../scripts/rehearse-local-recovery.mjs) verifies current free/paid access, learner isolation, submitted quiz history with immutable versions, durable topic completions, saved-position revisions and ten-day retention cleanup through actual database RPCs. Its corrupt-archive case removes referenced learners and verifies atomic rollback before restoring the valid archive. [Recovery tests](../tests/database/recovery.test.mjs) also cover malformed row JSON, unknown columns, changed manifests, schema drift, nonempty targets, exact bigint values and fixture cleanup.

The rehearsal also restores withdrawal records and stopped drafts, verifies that their questions stay hidden and save/submit remain denied, and checks that submitted results and history remain unchanged. The active catalog excludes a withdrawn current version.

A fixture-generated encryption key restores an authenticated session through the production encrypted-session adapter and service-only database RPC. A different key requires fresh sign-in, and explicit session invalidation removes restored authority. The key lives only in the rehearsal process. This check does not establish production key custody or hosted Auth token validity.

The rehearsal and durable-session tests share [database-session-fetch.mjs](../tests/support/database-session-fetch.mjs). That transport accepts only a live owned loopback database, the fixed synthetic RPC origin/key and allowed session arguments. It refuses remote origins and bearer tokens. Each request uses its own service-role transaction and closes the connection after success or failure.

Private media has its own synthetic file-copy and SHA-256 check outside the repository. Database backups contain Storage metadata, but not the object bytes stored through the Storage API. A real media recovery procedure must copy and verify those objects separately. See [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups).

## Hosted work still required

A real backup destination, schedule, retention policy, encryption-key custody and authorized hosted restoration require owner decisions and a separately approved operational procedure. Hosted recovery must include private-media bytes, actual provider Auth state and the configured cleanup jobs. A successful local report does not change deployment readiness, enable billing or authorize exporting production data. Use [Operations](OPERATIONS.md) and [Hosting preparation](hosting.md) for those boundaries.
